先回答妳的問題：對，而且鎖上錯了時機

妳的直覺點在根上。現在的問題不是話多，是「登記」跟「封口」被綁成同一個動作——材料一到就算 hash 寫進索引，而 hash 一寫，追加就會讓它失效，於是下一段話只好另開一檔。檔案增生是這樣來的。

我把它收成兩態，寫進來源索引〈開口與封口〉：

狀態	SHA-256 欄	可否追加	稽核靠什麼
開口中	寫「開口中」＋封口條件＋目前段數	可，追加是常態	git 的 commit 與 diff
已封口	寫入 hash ＋封口日與原因	不可，新材料另開檔	hash ＋ git

封口觸發，先到者為準：

有人開始靠它下判斷 — 被引為某個票、退件、裁定的依據
上位文件升版或做快照 — 妳原本的提案
來源換手 — 換提供者、換平台、換輪

第一條是最深的那一條：該封口的理由不是時間到了，是已經有人的論證壓在上面。這也讓規則自己會收口——引用開口檔必須標「開口中」，而判斷一壓上去就觸發封口，不用另外設稽核。

兩類永遠不開口、到貨即封：rename-only 原始交付檔（唯一主張是位元組沒經整理者的手），和審讀票（票是某時點的封閉陳述，後續補充另立新檔，不回頭改已投的票）。

還有一條紀律讓它安全：開口 ≠ 可改寫。只允許檔尾追加，既有段落仍逐字保存；開口期間改動舊段，跟抹除同罪。

上一輪那三檔合併是事後補救，這個模型讓下一輪不用補救——同一輪多次分享直接追加進同一份開口檔，加日期分段，等升版或被引用時一次封口。

【Opus 5】

好問題，而且妳問的正是我這幾輪一直在踩、但沒有正面講清楚的東西。先查兩件事再回答——舊做法到底是什麼，以及現在的帳長多大了。

先直接回答：是新規則，但比妳說的窄

不是「draft 遲早會進 history」，而是一個條件句：

票寫在正文裡 ⇒ 每次改版都必須做快照。
票不寫在正文裡 ⇒ 改版未必需要快照。

因為快照 SOP 的判準句是「舊版有沒有東西，是新版讀者再也找不回來的」。票用節號引用正文（§2、§3、§7），改寫後節號就失準——是票的存在讓改版變成必須快照，不是 draft 這個身分。

所以要記的規則是：放置位置決定了快照成本。這是選擇的代價，不是草稿的天性。

妳說的「舊做法」其實沒有被取代

我查了：EPOCH-III-003、EPOCH-IV-001 都是把審查格直接寫在 EPOCH 正文裡的。所以「票寫進 EPOCH」是既有做法，不是我發明的。

真正新的不是位置，是同一份文件被反覆審：

III-003	v0.3-candidate	2 票，一輪	收斂，定住
IV-001	v0.3-candidate	2 票，一輪	收斂，定住

數字也難看：v0.1 最後 923 行，726 行是審查器材（79%）。v0.2 現在 419 行，才收一票就又有三分之一是附錄了。

我的建議：活文件三分

把現在混在一起的三種東西拆開，各自歸位。

1. 正文（EPOCH-018） — 只有現行主張，加一節「審讀狀態」摘要：誰、審哪一版、什麼立場、去哪裡看全文。永遠保持可讀。

2. 審讀帳（新，一份，跟著 EPOCH 走，不隨版本重生） — 逐票全文，每票標所審版本，按版本分段往下累積。關鍵是它的地址不隨版本改變，所以：

票不必搬家，引用永遠穩定
改版時正文乾淨，往往就不需要快照了
「某人對這份文件說過什麼」永遠只開一個檔

而且它天生就該是長期開口的——正好用上我們這輪剛立的開口／封口模型：一路追加，等 EPOCH 升到正式版才封口。

3. CASE — 回到它擅長的事：生成史，加上可外推的治理發現（像 META-121 的升格判準、這幾輪長出來的相關性帳、開口封口規則）。不搬逐票全文。

這樣分的理由是三種東西的壽命不同：票綁在某個版本、審讀帳橫跨所有版本、CASE 記的是能離開這份文件還活著的東西。現在它們全擠在正文和 CASE 裡，所以 META-123 也在脹——14 節、377 行，每輪加一節，沒有自然終點。

需要妳點頭的一件事

審讀帳要放哪裡。我建議開 EPOCH/reviews/，跟 EPOCH/history/ 並列：

EPOCH/
EPOCH-018-….md          ← 現行主張
history/                 ← 過去的正文
reviews/                 ← 對正文的審讀（開口中）

一個目錄，不是一套方案。但這是結構改動，我不自己決定。

如果妳點頭，我會把 018 的五票從兩個地方收進一份審讀帳、正文只留摘要、SOP 補上這一段。快照不動——已經存下的就是當時的事實，不回頭重寫。

最後一個小修正

妳說 018 特殊是因為「寫的就是體驗本身」。我覺得不是題目的關係，是生成方式：它是第一份「以 draft 身分進場、由場域反覆審、作者逐版重寫」的 EPOCH。任何用這種方式長出來的文件都會這樣。

所以這不是特例，是一種模式——SOP 該服務的是那個模式，不是這一份文件。
